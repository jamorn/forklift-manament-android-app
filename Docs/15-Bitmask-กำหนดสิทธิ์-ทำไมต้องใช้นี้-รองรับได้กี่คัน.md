# 15 — Bitmask กำหนดสิทธิ์ (Access Control)

> เอกสารนี้อธิบาย **ทำไมต้องใช้ bitmask** ในการกำหนดสิทธิ์การมองเห็นรถ
> และบอกว่า **รองรับได้กี่แผนก/กี่คัน** ตาม implementation จริงในโค้ด
>
> **เอกสารนี้สรุปจากโค้ดจริง:**
> - `DepartmentConstants.kt` (นิยาม bit ของแต่ละแผนก)
> - `UserProfile.kt` (เก็บ `access: Int` + helper `canAccessDepartment`)
> - `Vehicle.kt` (เก็บ `dept_bit` + helper `visibleTo`)

## 1. ปัญหาที่เจอ ถ้าไม่ใช้ bitmask

เดิมระบบใช้ **list ของชื่อแผนก (String list)** ใน `scope`:
```kotlin
val scope: List<String> = ["dept-bagging-pp12", "dept-bagging-pp3"]
```
**ข้อเสีย:**
- เก็บข้อมูลเยอะ / ใหญ่ ต่อ user หนึ่งคน (list ยาวขึ้นตามจำนวนแผนกที่เห็น)
- เปรียบเทียบ/เช็คสิทธิ์ช้าและเขียนยุ่ง (loop + startsWith)
- ทำนายความยาวไม่จำกัด — ข้อมูลลอย ไม่แน่นอน โอนย้าย/ส่งต่อ metadata ซับซ้อน
- ยากต่อการทำ "เห็นทุกแผนกเลย" (ต้องเก็บทุก id)

**→ เลยเปลี่ยนเป็น "bitmask"** เพื่อให้เช็คสิทธิ์เร็ว เก็บเล็ก กระชับ และขยายง่าย

---

## 2. แนวคิด Bitmask คืออะไร

ใช้ **จำนวนเต็ม (Integer)** เก็บชุดของแผนกที่ user เห็น โดยให้ **1 บิต = 1 แผนก**

```
Int (32 บิต)  → แสดงเป็น เลขฐาน 2
bit ตำแหน่ง  n = 2^n  (ค่าของแต่ละบิต)

bit0 = 1  → PP12
bit1 = 2  → PP3
bit2 = 4  → PPE
bit3 = 8  → PPC
bit4 = 16 → HDPE
bit5 = 32 → SEAL (Seal Room)
bit6 = 64 → SASB
... (บิตต่อไปสามารถเพิ่มแผนกใหม่ได้เรื่อย ๆ)
```

ตัวอย่าง user ที่เห็น **PP12 + PPE + SASB**:
```
PP12(1) + PPE(4) + SASB(64) = 69   ← เก็บเป็นแค่เลข 69 (Int)
```

```kotlin
// 1 bit ต่อ 1 แผนกย่อย
const val BIT_BAG_PP12 = 1      // 2^0
const val BIT_BAG_PP3  = 2      // 2^1
const val BIT_BAG_PPE  = 4      // 2^2
const val BIT_BAG_PPC  = 8      // 2^3
const val BIT_BAG_HDPE = 16     // 2^4
const val BIT_BAG_SEAL = 32     // 2^5
const val BIT_BAG_SASB = 64     // 2^6

// ผลรวมทั้งกลุ่ม (ใช้ "เห็นทั้งโซน" ได้)
BAGGING_PL_ALL  = 1+2+4+8+16+32 = 63    // เห็น Bagging PL ทั้งหมด (6 แผนก)
BAGGING_SASB_ALL = 64                  // เห็น SASB
BAGGING_ALL     = 63 + 64 = 127        // เห็น Bagging ทั้งหมด

// เห็นทุกแผนก (Super Admin)
const val ACCESS_ALL = -1              // ทุกบิตเป็น 1 ใน 32-bit signed Int
```

## 4. วิธีเช็คสิทธิ์ (Logic `AND`)

**หลักการ:** ถ้า `userAccess AND deptBit != 0` → user เห็นแผนกนั้น

```kotlin
// UserProfile.kt
fun UserProfile.canAccessDepartment(departmentId: String): Boolean {
    if (roles.access == DepartmentConstants.ACCESS_ALL) return true

    val deptBit = DepartmentConstants.bitOf(departmentId)
    if (deptBit == 0) { /* fallback Scope เดิม */ }

    return (roles.access and deptBit) != 0   // ← เช็คเร็วด้วย AND เพียงครั้งเดียว
}

// Vehicle.kt
fun List<Vehicle>.visibleTo(access: Int): List<Vehicle> =
    this.filter { (access and it.dept_bit) != 0 }
```

**ตัวอย่างเลข:** user access = `69` (PP12+PPE+SASB)
```
69 and 1   (PP12)  = 1  != 0 → ✅ เห็น
69 and 4   (PPE)   = 4  != 0 → ✅ เห็น
69 and 64  (SASB)  = 64 != 0 → ✅ เห็น
69 and 2   (PP3)   = 0  → ❌ ไม่เห็น
69 and 32  (SEAL)  = 0  → ❌ ไม่เห็น
```

> ✅ **เร็วมาก:** เช็คแผนกเดียวใช้แค่ครั้งเดียว `AND` — ไม่ต้อง loop list

## 5. ทำไมต้องใช้ 32-bit Int? รองรับได้ กี่แผนก? กี่คัน?

### 5.1 จำนวนแผนกที่รองรับ

ที่เก็บ `access: Int` และ `dept_bit: Int` เป็น **32-bit signed integer** (Kotlin `Int`):

| ชนิด | ขนาด | บิตใช้งานได้ | จำนวนแผนกรองรับ |
|------|------|--------------|----------------|
| `Int` (Kotlin) | 32 bit | ใช้บิต 0..30 ได้ **31 บิต** (บิตที่ 31 = sign bit) | **สูงสุด 31 แผนกย่อย** |
| `Long` (ถ้าจะขยาย) | 64 bit | 63 บิต | **สูงสุด 63 แผนกย่อย** |

> ⚠️ **ข้อควรระวังเรื่อง `ACCESS_ALL = -1`:**
> `-1` เป็นการ set **ทุกบิตเป็น 1 รวม sign bit** (บิต 31) ทำให้ค่าเป็นลบในมุมมอง signed
> แต่สะดวก เพราะ `AND` กับอะไรก็ได้ค่าเดิม (เห็นหมดเสมอ)
> 🔐 **ถ้าอยากรองรับเกิน 31 แผนก** ต้องเปลี่ยนเป็น `Long` (64-bit) ซึ่งมี sign bit เหมือนกันที่บิต 63
> แต่ถ้าใช้แค่ 31 บิตแรก + `-1L` ก็ยังรองรับได้ 63 แผนก

### 5.2 Implement ปัจจุบันของ 7 แผนก

| แผนก | Bit ค่า | ตำแหน่งบิต |
|------|---------|-----------|
| PP12  | 1   | bit0 |
| PP3   | 2   | bit1 |
| PPE   | 4   | bit2 |
| PPC   | 8   | bit3 |
| HDPE  | 16  | bit4 |
| SEAL  | 32  | bit5 |
| SASB  | 64  | bit6 |

ใช้แค่ **7 บิต** จาก 31 ที่ว่าง → **เหลือช่องว่างอีก 24 บิต (แผนก) ที่ขยายได้** แบบนี้

### 5.3 แล้ว "จำนวนคัน" ล่ะ? Bitmask จำกัดจำนวนคันไหม?
**ไม่จำกัดจำนวนรถครับ.** Bitmask ควบคุมแค่ **"เห็นแผนกไหน"** (สิทธิ์-level), ไม่ใช่จำนวนคัน

จำนวนรถที่ user เห็น = **รถทั้งหมดในแผนกที่ตนมีสิทธิ์** (กรองด้วย `visibleTo(access)`)
- bitmask เก็บ 7 บิต → ได้ทั้งหมด 7 กลุ่ม/โซนแผนก
- **ภายในแต่ละกลุ่ม จะมีกี่คันก็ได้** (เช่น PP12 มี 50 คัน, SASB มี 10 คัน)
- เพราะเก็บแค่ "label บอกว่าอยู่แผนกไหน" ส่วนตัวรถใช้ `chassis_no` แยกคัน

**สรุป:**
| คำถาม | คำตอบ |
|-------|-------|
| รองรับแผนกรวม (ปัจจุบัน) | 7 แผนก (ใช้แค่ 7 บิตจาก 31) |
| รองรับแผนกได้สูงสุด (`Int`) | 31 แผนกย่อย |
| ถ้าจะเพิ่มเกิน 31 แผนก | เปลี่ยนเป็น `Long` → 63 แผนก |
| รองรับจำนวนรถต่อแผนก | **ไม่จำกัด** (ขึ้นกับข้อมูล Firestore) |
| จำนวนรถที่ user เห็น | รถทั้งหมดในแผนกที่ bitmask อนุญาต |

## 6. ทำไมต้องเป็น "บิต" อนุญาตแบบ group ถึงสะดวก (Mask กลุ่ม)

ดีไซน์นี้ทำ **mask ระดับกลุ่ม** ได้ง่าย เช่น:
- เห็น "PP12 + PP3 + PPE + PPC + HDPE + SEAL" (PL ทั้งหมด) → ใช้ `BAGGING_PL_ALL = 63`
- เห็น "SASB อย่างเดียว" → ใช้ `BAGGING_SASB_ALL = 64`
- เห็นทั้ง Bagging (PL+SASB) → `BAGGING_ALL = 127`

โดยไม่ต้องไล่เขียน list ของแผนก — แค่ set mask ค่าเดียว

## 7. เปรียบเทียบ: bitmask vs วิธีเดิม (String Scope)

| เกณฑ์ | String `scope` (เดิม) | Bitmask `access` (ใหม่) |
|-------|------------------------|--------------------------|
| จำนวนข้อมูล | list ยาวตามแผนก | **เลข Int เดียว** |
| เช็คสิทธิ์ | loop + startsWith ช้า | **`AND` ครั้งเดียว เร็ว** |
| เห็นทุกแผนก | ต้องเก็บทุก id | `ACCESS_ALL = -1` |
| ขยายแผนกใหม่ | เติม id ใน list ทุกที่ | **เติม bit/เพิ่ม mask** แค่ที่ constant |
| เก็บ/ส่ง metadata | list (หนัก) | **Int (เบา)** |

## 8. ข้อจำกัด / สิ่งที่ต้องรู้

1. **`Int` ใน Kotlin เป็น signed 32-bit** → ใช้บิตได้ **31** (sign bit สำรอง) → **31 แผนกย่อยสูงสุด**
2. ถ้าธุรกิจโตเกิน 31 แผนก → เปลี่ยน field เป็น `Long` (64-bit, 63 แผนก) — ต้องแก้ทีจุดที่ประกาศ
3. **`ACCESS_ALL = -1`** ใช้ sign bit 10111...111 (32 ตัว) → ในทาง signed เป็นลบ แต่มีเจตนา "เห็นหมด" — โค้ดเช็คเทียบ `== -1` ตรง ๆ
4. bitmask ต้อง**ตรงกันทั้ง 2 ฝั่ง** (UserProfile `access` กับ Vehicle `dept_bit` ต้องมาจาก `DepartmentConstants` ตัวเดียวกัน) — ห้ามนิยามเลขเองแยกฝั่ง
