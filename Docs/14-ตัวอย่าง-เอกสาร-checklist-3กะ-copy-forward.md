# 14 — ตัวอย่างเอกสาร Checklist ทั้ง 3 กะ ใน 1 วัน (พร้อม Copy-Forward)

> เอกสารนี้จำลองหน้าตา Doc ของแต่ละกะ (M / E / N) ใน **work-day เดียว (02 ส.ค.)**
> เพื่อให้เห็นว่า ระบบ "Copy-Forward" (pre-fill จากกะก่อน) ส่งผลต่อเอกสารแต่ละกะอย่างไร
>
> **สมมุติฐาน:** ตรวจรถ 1 คัน (FL-101) เพื่อให้ตัวอย่างกระชับ ระบบแยก Doc ต่อกะ ตาม Docs/13
>
> **สถานะ:** 📝 ตัวอย่างจำลองเท่านั้น ยังไม่ได้ implement

## 🧩 หลักการ Copy-Forward (ระบบที่มีอยู่)

จาก `ChecklistViewModel` (~บรรทัด 104-111):
```kotlin
// Copy-Forward: pre-fill results + remarks + meter จากกะก่อน
... copy(cs.remarks)
... mainRemark = cs.main_remark,
... meter = ...
```

เมื่อ operator เริ่มกะใหม่ ระบบ **copy ค่าจากกะก่อนหน้า** ขึ้นต้นให้:
| ฟิลด์ | copy จากกะก่อน หรือไม่ | เหตุผล |
|-------|----------------------|--------|
| `manhourMeter` | ✅ copy | กะถัดไปใช้เลขต่อจากกะก่อน (สะสมไมล์) |
| `main_remark` | ✅ copy แล้ว **overwrite** ได้ | เป็น **สภาพปัจจุบัน** ของรถ ณ กะนี้ |
| `remarks` (ต่อ item) | ✅ copy | เห็นสภาพเดิม/ที่กะก่อน fail (เป็น baseline) |
| `results` (pass/fail) | ✅ copy (แก้ได้) | เห็นผลเดิม แล้ว operator ตรวจของตัวเองใหม่ได้ |

## 🎯 หลักการสำคัญ 1: `main_remark` = "สภาพปัจจุบัน" (overwrite ถูกต้อง)

**เหตุผลทางธุรกิจ (จากผู้ใช้งาน):**
> กะ E ตรวจพบรอยร้าวกระจก → `unsafe` → **นำรถไปซ่อม**
> กะ N มารับกะ → รถ**ซ่อมเสร็จแล้ว กลับมา normal** → `main_remark` ใหม่จึงแทนที่ของเก่า

ดังนั้น:
- `main_remark` ต้องสะท้อน **"สภาพรถ ณ ตอนที่กะนี้ตรวจ"** (ปัจจุบัน) → **overwrite ถูกต้อง**
- รถซ่อมเรียบร้อย → `main_remark` = "ซ่อมแล้ว ปกติ", `status = normal` ✅

---

## 🎯 หลักการสำคัญ 2: เรื่อง "ไล่บี้คนทำ" / รูป / ซ่อม → ย้ายไป supervisor + LINE (ไม่ใช่งานระบบ)

**ตาม workflow จริง:**
> เมื่อพบปัญหา/ความเสียหาย (เช่น แก้วแตก) → operator **ถ่ายรูปลง LINE กลุ่ม**
> และปัญหานี้จะ**ย้ายไปให้ supervisor จัดการ** (แนบรูปว่ารถคันไหนเสียหายอะไร + ใส่หมายเหตุ)
> หัวหน้าไปไล่บี้หาคนทำตามรูป/หลักฐานใน LINE

**ผลต่อระบบ checklist:**
- ระบบ **ไม่ต้อง** รับผิดชอบ "การไล่บี้ / ประวัติการซ่อม / ว่าใครทำ"
- `main_remark` ไม่ต้องเก็บประวัติกะแบบ append (ไม่ต้องเก็บว่า "ใครเจอตอนไหน")
- ✅ ยืนยันความเรียบง่าย: checklist แค่บอก **สภาพปัจจุบัน** ของรถแต่ละกะเท่านั้น
- supervisor/ฝ่ายซ่อม ใช้ **LINE + รูป** เป็นหลักฐานจัดการคนละส่วน

## 🗂️ ภาพรวม: 3 Docs ของ work-day 02 ส.ค.

```
work-day (02 ส.ค.)
├── Doc กะ M  (06:00–14:00)   → date=2026-08-02, shift=M  (สภาพปกติ)
├── Doc กะ E  (14:00–22:00)   → date=2026-08-02, shift=E  (พบรอยร้าว → ไปซ่อม)
└── Doc กะ N  (22:00–06:00)   → date=2026-08-02, shift=N  (ซ่อมเสร็จ → กลับ normal)
```

> `date` ทั้ง 3 กะ = **02 ส.ค. เดียวกัน** (ใช้ work date) แต่ `shift` ต่างกัน + สมาชิกต่าง document
> 📌 กรณีพบปัญหาที่ต้องซ่อม → operator ถ่ายรูปลง LINE + แจ้ง supervisor (คนละส่วนกับ checklist)

## 🔁 สรุปการ copy-forward ระหว่าง 3 กะ

| ฟิลด์ | M (แรก) | E (copy จาก M) | N (copy จาก E) |
|-------|---------|----------------|----------------|
| `manhourMeter` | 12,450 | 12,480 (copy + อ่านเพิ่ม) | 12,520 (copy + อ่านเพิ่ม) |
| `main_remark` | "" | "พบรอยร้าว → ส่งซ่อม" | "ซ่อมแล้ว กลับปกติ" **(overwrite)** |
| `remarks` | {} | {กระจก:รอยร้าว} | {} (เคียร์แล้ว ซ่อมเสร็จ) |
| `results` | all pass | กระจก→fail | all pass |
| `status` | normal | unsafe → ส่งซ่อม | **normal** (กลับมา) |

**จุดสำคัญ:**
- `manhourMeter` — copy-forward แล้ว**เพิ่มต่อ** ถูกต้อง กะต่อเนื่องกัน
- `main_remark` — **overwrite** ถูกต้อง เพราะสะท้อน **สภาพปัจจุบัน** ของรถ กะต่อกะ
- **เรื่อง "ไล่บี้/รูป/ซ่อม"** — ย้ายไป **supervisor + LINE กลุ่ม** คนละส่วน ไม่ใช้ระบบ checklist

## 📝 ข้อสรุปแนวทางที่ถูกต้อง (สอดคล้อง Docs/13 + business logic)

1. **`manhourMeter`** → copy จากกะก่อน + operator อ่านเลขใหม่ (สะสมต่อ)
2. **`main_remark`** → copy มาเป็น baseline แล้ว **operator ตรวจ/แก้ของกะตัวเองได้ (overwrite)** — สื่อ "สภาพปัจจุบัน"
3. **`results`/`remarks`** → copy มา baseline แล้วแก้เป็นของกะตัวเอง
4. **`status`** → เปลี่ยนตามสภาพจริงของแต่ละกะ (normal → unsafe → ซ่อม → normal)
5. **งาน "ไล่บี้คนทำ" + รูป + การซ่อม** → **อยู่ในส่วนของ supervisor / LINE กลุ่ม** ไม่ใช่งานระบบ checklist
6. ใช้ **work date** (Docs/13) → 3 กะของคืนเดียวกัน `date=02` ตรงกัน
